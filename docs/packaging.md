# Desktop packaging — SelekyT for Windows and macOS

**Honest status of this document:** it describes an architecture, a set of
configuration files, and two CI jobs. **No native build has ever been executed
by the author of this work.** The development host is Linux x64 with no Rust
toolchain, no Node, and no Tauri CLI. What *was* verified on that host is
listed in "Verification evidence" below; what was not is listed in
"VERIFICATION REQUIRED ON". Treat every claim about Windows and macOS as
*designed*, not *observed*.

## Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│  SelekyT.app / SelekyT.exe   (Tauri 2 shell, apps/desktop/)       │
│  ┌────────────────────────────────────────────────────────────┐   │
│  │  webview: web/index.html + web/app.mjs (unchanged shell)   │   │
│  │     web/tauri-bridge.mjs routes /api/* to invoke()         │   │
│  └───────────────┬────────────────────────────────────────────┘   │
│                  │ Tauri commands (src-tauri/src/main.rs)          │
│  ┌───────────────▼────────────────────────────────────────────┐   │
│  │ selekyt_rpc(target, op, params) → JSON-RPC over stdio       │   │
│  │ selekyt_health()  → ping both sidecars                      │   │
│  │ prepend_bin_to_path() → resources/bin on PATH for the engine│  │
│  └───────┬───────────────────────┬──────────────────────────────┘   │
│          │ externalBin            │ externalBin                     │
│  ┌───────▼──────────┐   ┌─────────▼────────────────────────────┐   │
│  │ selekyt-mech     │   │ selekyt-python (python-build-        │   │
│  │ (rust/sidecar)   │   │  standalone 3.12.14) running         │   │
│  │ mechanical core  │   │  `-m selekyt --server`               │   │
│  └──────────────────┘   │ = the CLI's intelligence layer,      │   │
│                         │   pip-installed from this repo        │   │
│                         └───────────────┬──────────────────────┘   │
│                                         │ subprocess, PATH-scoped  │
│                         ┌───────────────▼──────────────────────┐   │
│                         │ resources/bin/ffmpeg, ffprobe (LGPL) │   │
│                         └──────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

Three properties the design is built around:

1. **One engine.** The packaged app runs `selekyt.server` — the same module the
   CLI and `selekyt --server` use — imported from the bundled interpreter's
   `site-packages`. There is no second copy of the scoring, segmentation,
   cut-algebra or rendering logic anywhere in the app. See
   [docs/desktop-bundling.md](desktop-bundling.md).
2. **A minimal permission surface.** The webview may read and write the user's
   own media/output directories and may execute exactly two programs, both
   declared Tauri sidecars. It has **no network permission of any kind**.
   ffmpeg/ffprobe are invoked by the Python layer over PATH, never by the
   rendered UI. See `apps/desktop/src-tauri/capabilities/main.json`.
3. **Reproducible provenance.** Every external binary is pinned by URL and
   sha256; a mismatch aborts the build. Each staged component ships a
   `*.sources.txt` next to it recording what it is and where it came from.

## Layout

```
apps/desktop/
  tauri.conf.json              the single packaging manifest (Tauri 2)
  package.json                 pins @tauri-apps/cli (the only npm dep)
  src-tauri/
    Cargo.toml / build.rs      the shell crate; codegen reads ../tauri.conf.json
    src/main.rs                sidecar lifecycle + the two Tauri commands
    capabilities/main.json     fs scope + the two sidecar execute grants
    icons/                     generated by icons/make_icons.py (pure Python)
  scripts/
    build_python.py            assemble + verify the bundled Python runtime
    fetch_ffmpeg.py            fetch + verify the LGPL ffmpeg (win/linux)
    build_ffmpeg_macos.sh      build LGPL ffmpeg from the pinned tarball
  resources/                   staging, produced by the scripts; not committed
    python/                    the interpreter + site-packages + sidecar name
    bin/                       ffmpeg, ffprobe, ffmpeg.sources.txt
    models/                    deliberately empty — see desktop-bundling.md
```

## Per-OS build commands

Everything below is what CI runs. Each step fails loudly (non-zero exit) if a
required tool or artifact is missing.

### Common prerequisites

```bash
# 1. Rust toolchain (cargo + rustc) and Node/npm must be on PATH.
# 2. The mechanical core, staged under its target-triple name:
( cd rust && cargo build --release --locked )
cp rust/target/release/selekyt-mech \
   apps/desktop/resources/selekyt-mech-<TRIPLE>   # .exe on Windows

# 3. The icons (pure Python, no PIL needed):
python apps/desktop/src-tauri/icons/make_icons.py
```

`<TRIPLE>` is `x86_64-pc-windows-msvc`, `aarch64-apple-darwin` or
`x86_64-apple-darwin`. CI derives it from the runner.

### Windows (windows-latest)

```bash
python apps/desktop/scripts/build_python.py  --triple x86_64-pc-windows-msvc
python apps/desktop/scripts/fetch_ffmpeg.py  --target win64
( cd apps/desktop && npm ci && npx tauri build --bundles nsis,msi )
```

Produces an NSIS installer and a WiX MSI under
`apps/desktop/src-tauri/target/release/bundle/`.

### macOS (macos-latest, Apple Silicon)

```bash
python apps/desktop/scripts/build_python.py  --triple aarch64-apple-darwin
bash   apps/desktop/scripts/build_ffmpeg_macos.sh
( cd apps/desktop && npm ci && npx tauri build --bundles app,dmg )
```

An Intel build is the same job with `--triple x86_64-apple-darwin`. Produces
`SelekyT.app` and a `.dmg`.

### Linux (development verification only)

```bash
python apps/desktop/scripts/build_python.py  --triple x86_64-unknown-linux-gnu
python apps/desktop/scripts/fetch_ffmpeg.py  --target linux64
```

No Linux desktop bundle is shipped; this exists so the assembly pipeline can
be exercised and smoke-tested on the dev host.

## Smoke test

`tests/test_desktop_smoke.py` is gated behind
`SELEKYT_DESKTOP_SMOKE=1` + `SELEKYT_DESKTOP_RESOURCES=<resources dir>` and
skips everywhere else. It asserts, against the *packaged* runtime:

- the bundled `selekyt-mech` answers `ping`;
- the bundled Python sidecar answers `ping` and reports a version;
- `shutil.which` inside the packaged runtime resolves to the bundled
  ffmpeg/ffprobe (not a system one) and the LGPL provenance file is present;
- a deterministic 1-second tone analysis completes with the network stack
  disabled (DNS and socket connect both raise), at the pinned 32 ms frame
  cadence.

## Interface surface introduced

**Tauri commands** (invokable from the webview):

| Command | Arguments | Returns |
| --- | --- | --- |
| `selekyt_rpc` | `target` (`"python"` / `"mech"`), `op`, `params` | the sidecar's JSON-RPC envelope verbatim |
| `selekyt_health` | — | `{"python": <ping envelope>, "mech": <ping envelope>}` |

**Configuration keys** (`apps/desktop/tauri.conf.json`):

| Key | Meaning |
| --- | --- |
| `bundle.externalBin` | the two and only two executable programs for the webview |
| `bundle.resources` | `python/`, `bin/`, `models/`, `share/` — staged by the scripts |
| `bundle.targets` | `app`, `dmg`, `nsis`, `msi` |
| `app.security.csp` | `'self'`-only; `connect-src` allows no external origin |
| `build.frontendDist` | `../web` — the existing shell, no second UI |

**Environment variables** (all documented, none invented):

| Variable | Used by | Meaning |
| --- | --- | --- |
| `SELEKYT_DESKTOP_SMOKE` | the smoke test | gate: only run on a packaging runner |
| `SELEKYT_DESKTOP_RESOURCES` | the smoke test | where the staged runtime lives |
| `SELEKYT_MECH` | parity + smoke tests | override the mech binary path |
| `SELEKYT_PYTHON` | `web/server.mjs`, smoke test | override the interpreter path |
| `PATH` (process) | the shell, via `prepend_bin_to_path` | how the engine finds the bundled ffmpeg |

Additionally exercised here, with real downloads from the pinned URLs (see the
"commands and output" section of the accompanying report):

- `build_python.py --hash-only` for **all four triples** — each pinned
  python-build-standalone URL resolves and its sha256 was recorded from an
  actual download;
- `fetch_ffmpeg.py --hash-only` for **win64 and linux64** — each pinned BtbN

- `build_python.py --triple x86_64-unknown-linux-gnu` (the full, non-hash-only

  and confirmed `sys.prefix` still resolves to the bundled tree and the

## VERIFICATION REQUIRED ON (never run on this host)

This is the part to read before trusting any of the above on Windows or macOS.
Each item has the exact command that closes it.

### A. Native compilation — never attempted

1. **The Tauri shell crate has never been compiled.** `src-tauri/build.rs`,
   `main.rs` and `Cargo.toml` are unverified Rust. Even the
   `tauri_build::Builder::tauri_conf("../tauri.conf.json")` call is an API
   shape I could not check without a toolchain.
   ```bash
   ( cd apps/desktop/src-tauri && cargo check )
   ```
2. **`tauri build` has never run**, so `tauri.conf.json` has never been
   validated by the real schema validator.
   ```bash
   ( cd apps/desktop && npx tauri build --bundles app,dmg )   # macOS
   ( cd apps/desktop && npx tauri build --bundles nsis,msi )  # Windows
   ```
3. **The capability file has never been applied.** In particular, whether
   `shell:allow-execute` with `sidecar: true` correctly admits a sidecar whose
   `externalBin` path is *inside* the resource directory (the trick that keeps
   the interpreter's `Lib/` tree adjacent) is unverified.
4. **Icons render correctly.** The PNG/ICO/ICNS writers self-verify structurally
   here, but whether the ICO/ICNS display correctly in Explorer/Finder is a
   native question.
5. **`tauri.conf.json` icons list** references `icon.icns`/`icon.ico`, which
   are generated by `make_icons.py` — confirm they exist before a manual
   `tauri build` outside CI.

### B. Interpreter renaming

`build_python.py` renames `python.exe` / `bin/python3.12` to
`selekyt-python-<triple>`. python-build-standalone locates its prefix relative
to the executable's *directory*, so the rename should be safe — and it was
*verified for the Linux triple* here (`sys.prefix` correctly points at the
bundled tree, and the renamed binary serves JSON-RPC). Windows and macOS were
never assembled:
```bash
apps/desktop/resources/python/selekyt-python-x86_64-pc-windows-msvc.exe \
  -c "import sys; print(sys.prefix, sys.executable)"
```

### C. Wheels install on the target

`pip install .` of this repository into the bundled 3.12 interpreter was
verified for the **Linux** triple — including `numpy`, `opencv-python-headless`,
`faster-whisper`, `ctranslate2`, `onnxruntime`, `av` and `yt-dlp`, all
resolving inside the standalone interpreter, with `import selekyt, engine.vad,
providers.ffmpeg` succeeding there. The Windows and macOS wheels must be
confirmed the same way on their own runners:
```bash
python apps/desktop/scripts/build_python.py --triple x86_64-pc-windows-msvc
python apps/desktop/scripts/build_python.py --triple aarch64-apple-darwin
```

### D. macOS ffmpeg source build

Never compiled anywhere. The configure line, the dylib-free static output and
the `shasum` pin check are all unverified. The `FFMPEG_SHA256` in
`build_ffmpeg_macos.sh` is a placeholder that **must** be replaced with the
digest the script itself computes (it prints the actual value and fails on
mismatch until then):
```bash
bash apps/desktop/scripts/build_ffmpeg_macos.sh
```

### E. End-to-end packaged behaviour

The smoke test's *skip path* and its *packaged-runtime path* were both
exercised on this host — the latter against the Linux-triple runtime, where
4 of its 5 tests passed and the fifth skipped for want of the Rust sidecar.
What has never run is the smoke test on a Windows or macOS packaging runner,
and the `selekyt-mech` leg of it has never run at all:
```bash
SELEKYT_DESKTOP_SMOKE=1 \
SELEKYT_DESKTOP_RESOURCES=apps/desktop/resources \
SELEKYT_MECH=apps/desktop/resources/selekyt-mech-<TRIPLE> \
SELEKYT_PYTHON=apps/desktop/resources/python/selekyt-python-<TRIPLE> \
  python -m pytest tests/test_desktop_smoke.py -q -rs
```

### F. Signing, notarization, and the WebView2 bootstrapper

Out of scope, and explicitly not claimed:
- macOS codesigning / notarization (`bundle.macOS.signingIdentity` is `null`);
- Windows Authenticode (`bundle.windows.certificateThumbprint` is `null`);
- the WebView2 bootstrapper download (`webviewInstallMode` is
  `downloadBootstrapper`) — a clean Windows 11 machine has Edge/WebView2
  already, but that assumption is untested.

### G. The webview transport bridge

`web/tauri-bridge.mjs` was never loaded inside a real webview. It is inert
outside Tauri by construction (`window.__TAURI__` absent), and the existing
Node harness tests still pass with it present, but the Tauri-side
`TAURI.core.invoke` shape is from the Tauri 2 docs, not from a running app.

## What is NOT built (deliberate)

- **Model pre-seeding** — no ASR model is bundled and there is no config switch
  to add one, because `providers/sherpa.py` resolves its model directory with
  no environment override. See `apps/desktop/resources/models/README.md`.
- **The `shell:allow-open` capability** — intentionally absent; the webview
  cannot hand a URL to the system browser.
- **Bridged harness conveniences** — the generated sample WAV and the
  `/api/file` download links work only over the Node harness. In the desktop
  shell you pick a WAV from disk. Recorded here, not hidden.
- **Linux desktop bundle** — Linux packaging is out of scope; the Linux
  triples in the scripts exist purely to verify the pipeline on this host.
- **Dev-server workflow** — `tauri dev` is not wired (there is no Vite dev
  server to proxy); the shipped bundles always embed `../web`.

## Relation to ci.yml

The two new workflows (`desktop-windows.yml`, `desktop-macos.yml`) are separate
files with their own triggers and never modify `.github/workflows/ci.yml`.
They only run when `apps/desktop/**`, `web/**`, `rust/**` or the Python
packages change, and both are also runnable via `workflow_dispatch`.
`tests/test_packaging_config.py` asserts that ci.yml does not reference them.
