# Product gap map

Where SelekyT is a finished product and where it is not, as of `08a94f1`.

The distinction this map exists to keep clear: **a stage whose code exists and
whose unit tests pass is not the same as a stage a user can rely on.** Each row
says what was actually exercised on this host, not what the code is capable of.

Host: Linux x86_64 (Azure datacenter), rustc 1.98.1, node present (no npm),
ffmpeg/ffprobe present, python3 + faster-whisper present. `yt-dlp` is installed
through the project venv — `yt-dlp>=2026.8.19` is a base dependency, not an
extra — and is only absent from a bare `PATH`, where `--doctor` correctly
reports it OPTIONAL. ollama and sherpa-onnx are not installed here; silero **is**
— the vendored `engine/models/silero_vad_v6.onnx` runs through onnxruntime, so
on this host the chain's preferred backend is a neural model, and the
energy-only case below is reached by forcing it or by running on a host without
the model.
Disk held ~15 GB free across this pass, enough to keep two real sources on disk
at once.

| Transcript-vs-audio coverage gate | complete, measured, and one real defect it had is fixed | the pipeline's only *hard* guard comparing the transcript against the audio it claims to describe (`engine.coverage`): a well-formed transcript covering a small fraction of audio that demonstrably carries speech raises rather than warns, because that is the shape of the corpus's most misleading shipped failure — `telugu-tutorial`, recorded OK with a transcript over **4.5%** of a 339.6 s file that is **77.4%** speech. **The defect was in the guard itself:** it constructed `EnergyVAD` directly, i.e. the one backend the chain ranks *last* — the level-blind one that scores a quiet whole file silent. On `hadhazy-protest` (mean −43.3 dBFS) the gate's own instrument read **0.0% speech**, so the ratio had no denominator and the verdict was `not_computable` on a source whose transcript covers 87.1% of it. The guard was blind on exactly the sources a collapse is most likely on. The gate now takes its audio truth from the same chain the pipeline prefers (silero → ffmpeg → energy), re-measured across all 11 corpus sources (`corpus/wer/runs/coverage-2026-09-27.json`): the ratio separates the one failure from the seven good sources with **nothing between them** — 0.058 vs a lowest-good 0.925, a 16× margin, and `COLLAPSE_RATIO` 0.25 sits inside that empty interval with 4× of room either side. Whisper is refused as audio truth by construction — it infers speech from transcript word timings, so the ratio would be ≈1.0 by construction and a collapse invisible. The gate is one-directional (a transcript covering *more* than the speech fraction is not evidence of anything) and it **degrades rather than passing**: below a 10% speech fraction the verdict is `not_computable` and says so, never `ok`. Pinned by `tests/test_coverage.py` (16 tests), including the probe-order regression and the whisper refusal. **Limits that remain:** no backend in the chain can tell speech from music, so a source that is mostly score with a little dialogue has a high speech fraction and a legitimately low coverage and would be flagged — the error cost is deliberately asymmetric (a false positive is a loud request to verify; a false negative ships wrong captions silently), and `--skip-coverage-check` records the measurement in `report.json` rather than deleting the evidence |

| Perception efficiency — read and inference | complete and measured, with three rejected alternatives on the record | the perception layer had no memory at all, and `scene_filter` asked for the same window twice per call — `analyse_scene` perceives it to decide the layout, the composition pass perceives it again to plan the trajectories, and before these caches the *second* ask re-ran the entire seek-and-decode pass *and* the entire detector pass. Found by counting, not by reading the call graph: one `scene_filter(30-45 s)` on the corpus AV1 source made **two byte-identical window requests and 56 detector calls for 28 frames**, costing 18.64 s. Fixed with a bounded LRU cache at that one choke point `_sample_frames` already served — frames first, then the perception derived from them, as a fifth slot on the same entry filled on first ask and left empty by the readers that only want pixels, keyed on video, size, mtime, window and sample count so an edited file is never served stale. One key, one bound and one eviction, so a perception can never outlive or out-grow the window it describes — an earlier pass had this as two parallel caches aligned by convention, which a fourth consumer would have had to learn. The perception entry also carries the detector that built it, so a replaced model makes every entry a miss rather than serving boxes the live model does not agree with. **Measured on the same window the baseline was taken on, before → after in one process: 18.43 → 11.17 s (1.65×, 7.26 s) for the read, then 11.14 → 9.33 s (1.19×, 1.81 s) for the inference on the composed path — 28 inferences instead of 56 — and 5.04 → 4.18 s (1.21×, 0.86 s) on the plain-speaker path, which has the same duplicate at a third site: `analyse_scene` perceives to decide the shot is a plain speaker, then `_probe_and_track` perceived it again to plan the crop, so the talking-head clip — the case the legacy chain was built for — did 56 inferences for 28 frames. 1.99× and 9.31 s saved per clip on the composed path, all with the shipped filter byte-identical throughout**, because a cache changes what is recomputed, never what the editor receives. The decode is 77% of the residual and is now irreducible at fixed sample count — reducing it means fewer samples or a codec path change, both of which alter results and neither of which is worth speculating about. Verified against a real ffmpeg-generated MP4 carrying both streams, plus the failure paths — non-media refused, a repeated name de-clobbered, a cross-origin POST rejected, and a connection that dies mid-body leaving no partial behind. Two things this does **not** establish: the largest body the route will accept is unmeasured here (the 32 GiB cap has never been approached — disk has ~1.3 GB free for most of this work), and the new intake has never been exercised with a genuine 1–3 hour master end to end through the pipeline, only with a 3 s file through the route itself |
| Desktop shell (Tauri) | incomplete, by environment | compiles and passes clippy, but no binary has been packaged on any platform and the webview has never rendered (no webkit2gtk). See `docs/agent-worktrees.md` |

## The critical path

Can a normal user provide a real long-form video and reliably receive usable
short-form edited videos?

**Yes — for a local file *and* for a URL, on a host with python3, ffmpeg,
faster-whisper and yt-dlp.** Both the CLI and the web shell complete the path,
the URL run used genuine unscripted human speech (NASA 360 Episode 5, 24:29),
and the outputs were inspected as files, not just as metadata: renders,
captions, per-cut EDL/FCPXML, QA and the editorial audit in
`tools/editorial_audit.py` were all green.

**Not demonstrated for a YouTube URL specifically.** The URL code path is
exercised end to end, but YouTube bot-blocks most videos from this host's IP
range. **One fetch has been observed** (an unauthenticated android client,
640×360, 213 s), while a second video was blocked during the same session, so
the block is per-video and intermittent rather than a hard IP ban — but **no
artifact from that fetch survives anywhere in this repo**, so it is an
un-artifacted session note, not evidence the path works. A user on a
residential IP should be unaffected; a user on a cloud VM will need
`--cookies`. That is the one input path this environment cannot verify.

Two further honest limits. The editorial gate used to have one observed
failure mode worth knowing about: a source with no detectable speech was
rejected with "No complete standalone stories passed the editorial/context
gate" rather than a message naming the actual cause. That was hit on
archive.org's `SVS-1335`, whose audio is digital silence (-91 dB); the empty
transcript and the rejection were both correct, but the error did not tell a
user that their file had no speech track. **It is fixed and no longer a
limit:** an empty transcript now fails before ranking, and the message is
chosen by what the audio actually showed — a peak-level measurement separates
a genuinely silent source from a damaged container, and reports the number so
the diagnosis is checkable rather than merely confident. Pinned by
`tests/test_speechless_source.py`, which asserts the expensive downstream
stages are never reached and that the wording does not imply the gate judged
anything.

A second failure mode with the same misleading message, found in the committed
corpus rather than on a live run: the Hindi interview carries **no terminal
punctuation anywhere** — no danda, no period, no question mark — so the
candidate scan had no signal that a thought had ended and closed no span at all
(52.76 s accumulated against a 53.00 s relief valve). The source reported that
no story passed the gate, when in fact nothing had been constructed to be
judged. **Also fixed:** the scan falls back to closing a span at its length and
word floors when no terminal mark is present, so the source is searched instead
of failing structurally. Verified against the committed transcript by executing
the pre-fix module alongside the current one (0 candidates → 6). The source
still ships no clips — the spans it now finds measure 0.53 best confidence
against a 0.75 floor, and are refused for a stated, measurable reason rather
than a structural one. Recorded in `docs/CORPUS_BENCHMARK_STATUS.md` and pinned
in `tests/test_unicode_pipeline.py`.

And no NLE on this host has opened an exported timeline, so format
validity is claimed, not import compatibility.
